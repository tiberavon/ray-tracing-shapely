# ray-tracing-shapely

A 2D optical **analysis and design** environment in Python, built on
[Shapely](https://shapely.readthedocs.io/) for geometry. It began as a
translation of a JavaScript interactive simulator and grew into something with
a different purpose.

## What it is for

Most 2D optics tools let you *watch* rays. This one lets you ask questions
about them afterwards, and lets you design a surface from what you want the
light to do.

Every traced ray keeps its lineage — a parent, a unique identity, the surfaces
it met and what happened at each one. That turns a simulation from a picture
into a record you can query: which paths reach the detector, how much energy
each carries, where two designs begin to differ, which rays are trapped by
repeated total internal reflection. Runs are stored and compared, so "did that
change help?" is a question with an answer rather than an impression.

On top of that sit layers the original simulator does not have:

- **Ray lineage as a graph** — parent/child tracking, structural path
  signatures, bidirectional tracing that connects a forward tree from the
  sources to a backward tree from the detector.
- **Nonimaging design** — CPC-family concentrators (DTIRC, angle transformer,
  RXI) and Miñano–Benítez Simultaneous Multiple Surface profile construction
  (RR / RX / RXI), on a reusable plane-curve toolbox. Surfaces are built from
  optical requirements, not from vertices typed in by hand.
- **Radiometry and eye safety** — unit-checked physical quantities, and
  exposure-limit routines for IEC 60825-1 (lasers) and IEC 62471 (lamps and
  LEDs), run as explicit state machines rather than nested conditionals.
- **An agentic surface** — the whole query layer is exposed as tools a language
  model can call, sharing one live kernel with the human at the notebook.
- **Run persistence** — parameter sweeps, stored results, cross-run
  comparison.

If you want an interactive simulator with a gallery of worked scenes, the
upstream [Ray Optics Simulation](https://github.com/ricktu288/ray-optics) is
better at that and always will be. This is for the case where the simulation
is the beginning of the work rather than the end of it.

## Install

```bash
pip install ray-tracing-shapely
```

The core install stays deliberately small — `shapely`, `numpy`, `sympy`,
`svgwrite`, `networkx`. The heavier layers are extras, so you only pay for
what you use:

```bash
pip install "ray-tracing-shapely[radiometry]"    # unit-checked quantities (pint)
pip install "ray-tracing-shapely[eye-safety]"    # IEC 60825-1 / IEC 62471
pip install "ray-tracing-shapely[agentic]"       # the MCP tool surface
pip install "ray-tracing-shapely[all]"           # everything
```

Python 3.11 or newer.

## Thirty seconds

```python
from ray_tracing_shapely.core.scene import Scene
from ray_tracing_shapely.core.scene_objs import Glass, SingleRay
from ray_tracing_shapely.core.simulator import Simulator

scene = Scene()
scene.color_mode = 'linear'

prism = Glass(scene)
prism.path = [
    {'x': 100, 'y': 50,  'arc': False},
    {'x': 200, 'y': 50,  'arc': False},
    {'x': 150, 'y': 150, 'arc': False},
]
prism.refIndex = 1.5
scene.add_object(prism)

ray = SingleRay(scene)
ray.p1 = {'x': 50,  'y': 100}
ray.p2 = {'x': 100, 'y': 100}
scene.add_object(ray)

segments = Simulator(scene, max_rays=1000).run()
print(f"Traced {len(segments)} ray segments")   # Traced 16 ray segments
```

Sixteen segments from one incident ray: it refracts into the glass, reflects
internally, and splits at each surface it meets. Render the result as SVG with
`SVGRenderer`, and every element it draws carries the identity of the ray or
object that produced it, so a diagram can be clicked back to the simulation
that made it.

## Documentation

The code is documented in two layers, both shipped with the package:

- **`dev_doc/concepts/`** — why the code has the shape it has. Thirty-six
  numbered concepts, each stating one claim and the evidence for it, written
  for a reader who wants to understand the design rather than just call it.
- **`dev_doc/architecture/`** — what is true now: a component map, a port
  register, and contracts stating what each boundary assumes and guarantees.

Docstrings cite both, so a question that starts in the code has somewhere to
go.

## Status

Early development, and honest about it: the translation of the original
simulator is not complete, and the API is not yet stable. Issues and
descriptions of what you are trying to do are the most useful contribution
right now — more useful than pull requests, which the project is not yet set
up to accept.
